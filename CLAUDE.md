# CLAUDE.md

Guidance for AI agents working in this repo.

## The concept (know this before making product decisions)

**The core concept:** VibeXP is "one shared brain" for a team's AI tools. Four resource types — **prompts** (reusable, composable with `{{variables}}` and references), **blueprints** (per-tool rules: Claude Code, Cursor, Codex), **memory** (what the AI learns), and **artifacts** (versioned AI output) — all live in a team workspace that every MCP-compatible tool connects to.

**The differentiator is the loop, not the storage.** What separates VibeXP from a prompt folder or a notes app: the AI *reads* context before a task, *writes back* lessons/memory/artifacts as it works, and every session compounds for the whole team. Read → work → write back → richer next session. Plus AI Feeds for steering autonomous agents, semantic search across everything, and GitHub import for bootstrapping. Free, open-source, self-hostable, works solo first, compounds with a team.

Judge features against this: anything that depends on humans hand-maintaining context fights the differentiator; anything that strengthens the automatic read/write-back loop reinforces it. (Marketing source of truth: the website repo's `/how-it-works` page.)

## What this is

**VibeXP**: open-source, self-hostable AI command center (prompts, memories, artifacts, agents, MCP integrations for Claude Code, Cursor, VS Code, etc.). Monorepo shipped as a **single combined Docker image** (issue #61): the Go backend embeds the built frontend SPA and serves it *and* the API from one port — `docker run ghcr.io/vibexp/vibexp`. Two source components, one deployable artifact:

- **`backend/`**: Go REST API (module `github.com/vibexp/vibexp`). Spec-first OpenAPI, PostgreSQL + pgvector, MCP endpoint, pluggable identity-provider auth (Google/GitHub/generic OIDC). Also embeds + serves the SPA (`internal/server/spa.go`, behind the `embedfrontend` build tag) and renders runtime `/config.js`.
- **`frontend/`**: Vite + React + TypeScript SPA. Built to `frontend/dist`, embedded into the backend for release; served by the Vite dev server in local development.

The frontend consumes two npm packages that are NOT in this repo: `@vibexp/api-client` (typed client generated from `backend/openapi.yaml`) and `@vibexp/design-system` (shared UI).

## Local development: use `make`

The root `docker-compose.yml` runs the published images (self-host), not for developing. Develop via the Makefile:

- Backend: `make backend-run-dev` (Postgres + air hot-reload), plus `backend-test`, `backend-lint`, `backend-check`, `backend-generate-openapi-server`, `backend-wire-gen`, `backend-mock-generate`.
- Frontend: `make frontend-run-dev` (Vite, http://localhost:5173), plus `frontend-install`, `frontend-lint`, `frontend-type-check`, `frontend-test`, `frontend-build`.
- Go toolchain is pinned: the Makefile sets `GOTOOLCHAIN=go1.25.13`. Keep `GO_VERSION` in sync with `go-version` in `ci.yml`.

## Generated code — never hand-edit

These artifacts are **generated and committed**. Change the *source*, run the regenerate command, commit the output. Never edit a generated file directly, and never make a drift failure go away with `git checkout` — the diff is the symptom, the stale source is the bug.

| Artifact | Committed paths | Regenerate with | Gate |
|---|---|---|---|
| oapi-codegen strict-server bindings (one package per spec-first domain) | `backend/internal/server/gen/**/*.gen.go` | `make backend-generate-openapi-server` | CI (`openapi` job) |
| mockery mocks (~124 files) | `backend/**/mocks/mock_*.go` | `make backend-mock-generate` | CI (`unit` job) |

Mock generation runs **without `--all`** (#678): the per-package `interfaces:` lists in `backend/.mockery.yaml` are authoritative, so mockery emits exactly those interfaces. **Adding a mockable interface means adding its entry to `.mockery.yaml` first** — a mock committed without an entry disappears on the next regenerate and fails `backend-mock-check`.
| Wire DI bindings | `backend/internal/container/wire_gen.go` | `make backend-wire-gen` | CI (`unit` job) |
| Config JSON schema | `backend/config.schema.json` | `make backend-generate-config-schema` | CI (`unit` job) |
| Embedded OpenAPI bundle (served at `/openapi.{yaml,json}`) | `backend/internal/server/openapispec/openapi.bundled.{yaml,json}` | `make backend-generate-openapi-bundle` | CI (`openapi` job) + pre-commit |
| JS + Go API clients | *not in this repo* | automatic on merge to `main` | see the API change flow below |

Mind the two suffixes: oapi-codegen writes `*.gen.go` (**dot**), Wire writes `wire_gen.go` (**underscore**) — a glob for one does not match the other.

Every gate is a regenerate-then-`git diff` target (`make backend-<x>-check`), so you can run it locally exactly as CI does. A drift gate is only meaningful against a **pinned** generator, so all of them are: `GO_VERSION` / `REDOCLY_VERSION` / `MOCKERY_VERSION` in the Makefile, and `wire` + `oapi-codegen` via the `tool` directive in `backend/go.mod`. Bump a pin deliberately and commit the regenerated output in the same change.

## Pre-commit hooks are MANDATORY

`.pre-commit-config.yaml` gates every commit on the CI checks (gofmt, golangci-lint, govulncheck, gosec, OpenAPI validation, frontend lint/type-check/test/build, gitleaks, policy hooks).

- Install once per clone: `pre-commit install` (needs `pre-commit`: `pipx install pre-commit` or `brew install pre-commit`).
- Before committing, verify it is installed. If `pre-commit` is missing, STOP and ask the user to install it. Do not proceed.
- Never bypass the hooks (`git commit`/`push --no-verify` or `-n` is forbidden). If a hook fails, fix the cause.

## Conventions & gotchas

- **Spec-first backend.** `backend/openapi.yaml` (bundled from `paths/` + `schemas/`) is the source of truth. Generated code (oapi-codegen server, Wire, mocks) is committed and must never be hand-edited — see [Generated code — never hand-edit](#generated-code--never-hand-edit) for the exact paths, regenerate commands, and drift gates. Generated files must stay `gofmt -s` clean (CI enforces).
- **Authorization goes through `internal/authz` — never re-implement the matrix (epic #220).** That package **is** the permission spec: the role→permission table (owner/admin/member) lives in `matrix.go` and the 14 dot-namespaced `Permission` constants in `permission.go`. Rules: (1) a service method that **mutates team-scoped data** must authorize via `services.AuthorizationService` (`Can` / `Authorize` / `CanActOnResource` for own-vs-any) rather than checking a role inline — prefer `Authorize`, which hands back the resolved role so you can echo it without a second lookup; (2) **no role predicates in repository SQL** (decision D3) — repositories are tenancy-only, and `TestNoRolePredicatesInRepositorySQL` fails the build if a `role IN (...)`-style predicate reappears; (3) the permission strings are **published API surface** (the `permissions` array on team payloads, #224) and are pinned to the spec enum by `TestTeamPermissionsEnumMatchesAuthzConstants` — renaming one is a breaking change, so change the constant and `schemas/teams.yaml` together; (4) clients (incl. the SPA) **gate on the server's `permissions` array, never on `role`** — the matrix lives here, and UI gating is convenience only since every write is authorized server-side regardless.
- **API change flow.** Update the spec (`backend/openapi.yaml` / `backend/paths/**` / `backend/schemas/**`) -> merge to `main` -> **both** generated clients publish **automatically** -> bump the frontend dep (and any Go consumer). The two clients are `@vibexp/api-client` (npm, source `vibexp/api-client-js`) and `github.com/vibexp/api-client-go` (Go module, source `vibexp/api-client-go`). **Do NOT hand-publish/hand-tag either client** (no manual `workflow_dispatch`, no GitHub Release, no `git tag` for a spec change): merging a spec change to `main` fires `.github/workflows/publish-api-client.yml`, which dispatches *both* downstream workflows — the api-client-js Publish and the api-client-go Release — and each **auto-minor-bumps** its own version off its latest release (every spec change = one new minor per client, breaking or not). The Go client "publishes" by committing the regenerated `vibexp.gen.go` and pushing a `vX.Y.Z` git tag (Go resolves modules from source at the tag — there is no registry); it stays on **v0.x** deliberately, since Go's semantic import versioning would force a `/vN` module-path suffix at v2+. Publishing by hand on top of the automation races it and can waste/duplicate a version. Only the frontend dependency bump remains manual (out of scope for the automation). Cross-repo trigger uses the "VibeXP Bot" GitHub App (installed on both client repos, **Actions: read/write** only — the Go tag push uses api-client-go's own in-repo `GITHUB_TOKEN`, not the app; secrets `VIBEXP_BOT_APP_CLIENT_ID` / `VIBEXP_BOT_APP_PRIVATE_KEY` on this repo). Tracking: #303 (JS), #329/#330 (Go).
- **Response conformance is progressive (tracked in #122).** The backend is spec-first for routing/request types, but response bodies are still largely hand-marshaled (`map[string]interface{}` / bespoke `models.*` structs) and **not checked against the schema**, so spec↔backend response drift ships silently (it has crashed the frontend three times: #105 / #121 / #132). We are closing this **domain-by-domain, not in one campaign**. **Whenever you touch a documented domain, leave it more conformant than you found it:** (1) return `oapi-codegen` strict-server generated response types, not `map[string]interface{}` / bespoke structs; (2) add a spec-validated response assertion (`specconformance.AssertConformsToSpec`) in the handler test and delete that op's entry from the payload-coverage ledger (`internal/server/openapi_payload_coverage_test.go`); (3) never serialize a required array as `null` — for a documented response with a *required* array field, declare it `models.JSONArray[T]` (a `[]T` whose `MarshalJSON` emits `[]` for nil), which guarantees `[]` by construction regardless of test coverage (issue #125, "Layer C"). `models.JSONArray[T]` is assignable to/from `[]T`, so only the field declaration changes; keep a plain `[]T` for arrays the spec marks nullable (`x | null`, e.g. `Prompt.labels`, `AgentStatsResponse.recent_activities`). The invariant is CI-enforced by `TestRequiredResponseArraysNeverNull` (`internal/server/required_array_null_test.go`), which derives every required-array response field from the spec (`specconformance.RequiredArrayFields`) and fails if one is not shim-protected — a new such field must be added to that test's registry (and use `JSONArray[T]`) or the documented ad-hoc allowlist. **New endpoints are non-negotiable:** they must ship strict-server-typed and ledger-covered (both gates are already CI-enforced), so the backlog never grows. Update the per-domain checklist in #122 as you go.
- **Single combined image / same-origin.** The backend embeds and serves the SPA from the same origin as the API (relative `VITE_API_BASE_URL=/api/v1`), so there is **no nginx proxy, no `BACKEND_ORIGIN`, and no CORS** in production. The SPA is registered as the chi `NotFound` catch-all (`internal/server/spa.go`) so it never shadows API/MCP/OAuth routes and stays invisible to the OpenAPI drift/coverage gates. The embed is behind the `embedfrontend` build tag (`spa_embed.go`); the **default build has no frontend** (`spa_noembed.go`) so the backend compiles/tests/runs with no `frontend/dist` (local dev + CI).
- **Runtime frontend config (`/config.js`).** Deploy-time, non-secret frontend values (branding/MCP endpoint/optional GTM) are env vars on the backend (`Config.RuntimeFrontendEnv`), served as `window.__VIBEXP_ENV__` via `/config.js` and read by the SPA through `getEnv()` (`src/lib/runtimeEnv.ts`), with build-time `import.meta.env` as the fallback. Self-hosters reconfigure with an env var + restart, no rebuild. Local dev (no backend `config.js`) uses the build-time fallback.
- **Config is a required `config.yaml` (koanf, epic #68).** The backend loads a nested `config.Config` from a **required** `config.yaml` (`internal/config`), resolved from `--config` → `$VIBEXP_CONFIG_FILE` → `./config.yaml`, with `${VAR}` / `${VAR:-default}` / `$${literal}` interpolation of string scalars from the environment; a missing file fails fast. Two committed surfaces: **`backend/config.example.yaml`** is the DEV-TUNED documented surface (localhost, Mailpit; copied to a gitignored `config.yaml` by `scripts/sync-env.sh` for `make backend-run*`), and **`backend/.env.example`** holds only the `${VAR}` secrets. `backend/config.schema.json` is generated (`make backend-generate-config-schema`, drift-gated). Adding a field: edit the `Config` struct + `defaults()` + `config.example.yaml`, regenerate the schema. Fields are optional in the schema — anything omitted from a config file inherits `defaults()`.
- **Combined image config is baked + env-driven (deploy-anywhere, #71).** The published image bakes **`backend/config.docker.yaml`** at `/app/config.yaml` (`VIBEXP_CONFIG_FILE` points there): a PRODUCTION-NEUTRAL counterpart to `config.example.yaml` where every operator knob is a `${VAR:-default}` reference, so `docker run -e ENCRYPTION_KEY=... -e DB_HOST=...` configures a container with env alone (one-command experience preserved). Operators mount their own file over `/app/config.yaml` for full control. It is schema-validated **and** load-tested (`config_docker_test.go`). The dev-login bypass / auto-enabled local MCP are gated by `IsLocalDevelopment()` (localhost `frontend.base_url`), so `FRONTEND_BASE_URL` is the real production switch — not a separate `DEV_LOGIN_ENABLED` env. `docker-compose.yml` sets secrets + non-default knobs as env consumed by those `${VAR}` references (no flat env the loader can't read).
- **Embedded MCP Authorization Server is HTTPS-only.** The AS endpoints (`/oauth2/*`, `/.well-known/oauth-authorization-server`) are wrapped by `requireHTTPSMiddleware` (`internal/server/middleware_https.go`) in `setupOAuthASRoutes`: a non-HTTPS request (no `r.TLS`, `X-Forwarded-Proto != https`) is rejected with 403 unless `Config.IsLocalDevelopment()`. VibeXP is deploy-anywhere, so this assumes TLS terminates upstream and the proxy forwards `X-Forwarded-Proto: https` (document this for self-hosters). Local dev + the e2e stack (localhost) are exempt.
- **No service worker, and no Firebase.** The frontend registers no service worker at all: there is no PWA/precaching SW, and the on-demand `firebase-messaging-sw.js` went with Firebase web push (#688 — the whole FCM stack, `device_tokens`, the `firebase` npm + `firebase.google.com/go/v4` deps and seven `VITE_FIREBASE_*` vars). `src/utils/serviceWorker.ts` + `public/{sw,dev-sw}.js` now evict *every* legacy worker. Don't reintroduce a precaching SW without a cleanup story, and don't reintroduce Firebase — #320 established its replacement token API cannot be targeted by the Go Admin SDK at all.
- **Vitest is the frontend test runner; `tsc -b` is what type-checks (#498).** The suite moved from jest/ts-jest to Vitest in #498 (react-router v8 is ESM-only and cannot load under jest's CommonJS transform at all). Config lives in `frontend/vitest.config.ts` (jsdom environment, `globals: true`, `setupFiles: ['./tests/setup.ts']`, v8 coverage writing `frontend/coverage/lcov.info` with `SF:` paths relative to `frontend/` — the Sonar rewrite in `ci.yml` still prefixes them). Two Vitest-specific traps the migration hit: (1) `vi.mock` factories referencing top-level `const` mock variables hit a hoisting TDZ (`Cannot access 'mockX' before initialization`) — declare those variables with `vi.hoisted(() => ...)`; (2) `vi.doMock`/`vi.mock` with a **relative** specifier resolves it from the *source* file being mocked, not the test file, so an aliased import in the source must be mocked by its alias (`'@/utils/environment'`), while a relative import must be mocked by the *exact* relative specifier — jest's moduleNameMapper specifier-remapping does not exist here. Type errors are caught by `make frontend-type-check` (`tsc -b`), which must keep covering **all three** test-bearing trees: `tsconfig.app.json` (`include: ["src"]`, so the test files under `src/` too), `tsconfig.test.json` (`include: ["tests"]`) and `tsconfig.e2e.json` (`include: ["e2e"]`, added in #621 — the Playwright tree sat outside every program for months, hiding 182 errors behind a green lint). Adding a test directory outside those three silently drops it from type-checking, and ESLint covering it is not the same thing.
- **No frontend telemetry.** The frontend bundles no error-tracking/maintainer telemetry (Sentry was removed in #58). `ErrorBoundary` and other error paths log via `console.error` only, and the build emits no source maps (`vite.config.ts` `build.sourcemap: false`). A self-hoster wanting error tracking can wire their own.
- **chi hands back percent-encoded path params — decode with `url.PathUnescape`, never `QueryUnescape` (#251/#257).** chi routes on `r.URL.RawPath` whenever the request path contains percent-encoding (`go-chi/chi/v5` mux), so `chi.URLParam` returns the **still-encoded** segment. Any path param that can carry reserved characters (invitation/share tokens, `slug` — generated from user names so a literal `+` is plausible — anything non-opaque) must be explicitly decoded before use, or an exact-match lookup misses on every request (the #251 invitation-accept bug). Decode with **`url.PathUnescape`**, not `url.QueryUnescape`: the two differ only on `+`, which `QueryUnescape` turns into a space (correct for query strings, silently corrupting for a path segment). Keep the existing 400-on-decode-error behavior. Opaque tokens you mint should be **unpadded** URL-safe by construction (`base64.RawURLEncoding`) so there is nothing to encode in the first place. Pure-UUID params can't contain reserved chars and don't need decoding.
- **Documentation belongs in `vibexp/docs`, and this repo has no `docs/` directory (#608).** Every user- and contributor-facing doc goes to the [docs repo](https://github.com/vibexp/docs) (published at docs.vibexp.io) — including upgrade/breaking-change notes, which have a standing home at `user-guide/self-hosting/upgrading`. The `docs/` tree here was deleted because a second docs home only ever drifts — it held exactly two files and they demonstrated both failure modes: an upgrade guide already re-authored into the docs site and never removed here, and a frontend API-integration guide that was real content no reader of docs.vibexp.io could find. A `no-docs-directory` pre-commit hook (`language: fail`, `files: ^docs/`) now rejects anything staged there. **The exception is code-adjacent documentation** — a package-level `README.md` next to the code it describes (`backend/internal/observability/metrics/README.md`, `frontend/e2e/journeys/README.md`), plus the root `README.md` and this file. Adding a docs-site page means a PR in `vibexp/docs`; remember its rule that **docs track the latest published release, not `main`**, so a page describing unreleased work waits for the release.
- **Secrets.** `.env` is gitignored, never commit it; only `.env.example` is tracked, with neutral values (e.g. `example.com`) since this is public and self-hosted.

## CI & releases

- CI runs the same `make` targets, so run them locally first. Since #638 the backend fans out into four parallel jobs instead of one serial `Build & Test`: **`unit`** (download-deps -> format -> build -> generated-code drift gates -> `backend-test-unit-coverage`, no Postgres service), **`integration`** (`backend-test-integration-coverage` against a Postgres service container), **`security`** (`backend-vulncheck` + `backend-security`) and **`lint`** (golangci-lint), plus OpenAPI validation and a PR-only **`migrations`** job (merge mode of `.github/scripts/check-duplicate-migrations.sh`, #710: fails a PR whose migration version numbers resolve to different filenames than `origin/main` — the collision local checks can't see; the `migration-renumbering` label is the escape hatch for deliberate renumberings like post-release consolidations, and labels are read at event time, so label first or re-run the job after labeling). The frontend likewise splits into **`frontend-static`** (lint -> audit -> type-check) and **`frontend-test`** (test-with-coverage -> build); `frontend-test` is the one Sonar waits on, and CI installs with `make frontend-ci-install` (`npm ci`) while `make frontend-install` stays `npm install` for local work. (Backend CI's `make backend-build` is the default no-embed build, which also guards "the backend builds with no `frontend/dist`".)
- **The Go suite is sharded; the two halves must stay exhaustive together (#638).** `backend-test-unit-coverage` runs the whole module *untagged*; `backend-test-integration-coverage` runs `-tags=integration` over exactly the two packages that carry `//go:build integration` files (`internal/repositories/postgres`, `internal/services/projectmigration`). **Adding an integration-tagged file to a third package means adding that package to the integration target**, or its tagged tests silently stop running in CI. `backend-test-coverage-integration` (both in one process) is kept as the local one-shot. Each job publishes its own profile and `sonar-project.properties` lists both in `sonar.go.coverage.reportPaths`.
- **CI caching is explicit; `main` is what keeps it warm (#638).** `actions/setup-go`'s built-in cache is off (`cache: false`) everywhere: it keys on Go version + `go.sum` only, so the key hit every run and the action therefore never saved. **That stale blob was not worthless** — it held the compiled stdlib and dependencies, which is why turning it off without replacing that floor measurably *regressed* CI (`Build` 3s→146s, gosec 44s→173s, golangci-lint 81s→224s); it only lacked this repo's own packages in `-race -cover` mode. In its place: a module cache on a stable `go.sum` key, and a **single shared** `~/.cache/go-build` cache keyed on `go.sum` + commit SHA, restored by *every* Go job (`unit`, `integration`, `security`, `lint`, `openapi`). The `unit` job is the sole saver — it compiles the module both plain and `-race -cover`, so its entry is a superset — and it saves on **pushes to `main` plus on a total cache miss** (`cache-matched-key == ''`). That second condition is load-bearing: without it the first runs after a landing or an eviction have nothing to restore and every Go job pays a full cold compile. It cannot run away, because once any entry exists the restore-keys ladder always matches, so PR runs stop saving. The entry is ~500-580MB; unconditional per-run saves would exhaust the 10GB repo limit in ~20 runs. Note a cache saved on a PR ref is visible only to that PR — only `main`'s entry serves everyone. Same restore-always/save-on-main pattern for the golangci-lint analysis cache; the pinned tool binaries (`govulncheck`, `gosec`, `golangci-lint`) are cached on their version strings, so bumping a pin re-installs automatically.
- **A warm build cache also warms Go's TEST-RESULT cache — expect `(cached)` (#638).** With `~/.cache/go-build` restored, `go test` returns stored results for any package whose inputs are byte-identical, so a PR touching only workflows/docs/frontend can finish the `unit` job in ~80s having executed **no** Go tests (every line reads `ok … (cached)`). This is Go's content-addressed cache and it is trustworthy, but it makes CI timings **non-comparable** unless you check: to benchmark the suite you must force execution with `-count=1`, or the number you measure is the cache. It also means "the unit job got faster" is not by itself evidence the tests still pass — read the log for `(cached)`.
- **`ci.yml` cancels superseded PR runs; `main` runs are neither cancelled nor queued.** `cancel-in-progress` is restricted to `pull_request`, because a `main` run is the Sonar coverage baseline and cancelling it would swing overall coverage (the #300 invariant). The group is `ci-${{ github.event.pull_request.number || github.run_id }}` — note the fallback is **`github.run_id`, not `github.ref`**: keying non-PR runs on the ref puts every `main` push in one group, and with cancellation off they then run strictly one-at-a-time, delaying the Sonar analysis, the signal on a broken `main`, and the cache-saving run. `run_id` is unique per run, so `main` pushes never contend. This is a correctness fix, not a latency one: per the Actions docs a **pending** run is cancelled by default when a newer run joins its group (`cancel-in-progress` governs only the *in-progress* run, and at most one run may be pending), so a shared `main` group silently drops the middle run of any three rapid merges — losing that commit's coverage baseline.
- **Dependency security runs in CI, not only pre-commit (#547).** `make frontend-audit`, `make backend-vulncheck` and `make backend-security` are CI steps, so a contributor without pre-commit installed no longer bypasses every dependency check. The two Go tools run in `ci.yml`'s own **`security`** job (split off the test job in #638) and are **pinned there** (`govulncheck@v1.6.0`, `gosec@v2.28.0`) for the same reason golangci-lint is (pinned at **v2.12.2** in the `lint` job; its findings over the old v2.5.0 pin were triaged in #554 — test-file gosec/prealloc noise is excluded config-first in `.github/linters/golangci.yml`, the two real hits fixed in code) — an unpinned bump turns a new upstream rule into a surprise red build on untouched code. **Install those exact versions locally** (`go install golang.org/x/vuln/cmd/govulncheck@v1.6.0`, `go install github.com/securego/gosec/v2/cmd/gosec@v2.28.0`): the pre-commit hooks invoke whatever binary is on `PATH`, so a version skew either way reports failures CI does not. The 7 findings gosec v2.28.0 added over v2.24.7 (6× **G124** cookie attributes, 1× **G710** open-redirect taint) were triaged in #553 and were **all false positives** — G124 demands a *literal* `Secure: true` and cannot evaluate the environment-derived value the cookie writers use, and it does not distinguish an outbound request cookie (where the attributes are meaningless per RFC 6265) from a response one; G710 flags a redirect built entirely from server-side config. Each site carries a `#nosec` with that reasoning, and the cookie attributes are pinned by tests instead. `.github/dependabot.yml` (npm `/frontend`, gomod `/backend`, github-actions `/`) keeps the lockfiles moving weekly; its PRs carry `no-issue-needed` so `pr-linked-issue.yml` passes.
- **One artifact, one workflow.** A GitHub Release `vX.Y.Z` (workflow `release.yml`) builds the single combined image `ghcr.io/vibexp/vibexp:X.Y.Z` (+ `:latest`, which docker-compose tracks) — the Dockerfile (`backend/Dockerfile`, built from the repo root) builds the frontend, embeds `dist`, and builds the Go binary with `-tags embedfrontend`. There is no separate frontend image.
- **`:latest` tracks the highest published semver, not "the most recent build" (#747).** The tag is enabled by a `Decide whether this build moves :latest` step that compares the version against every published non-prerelease release, *not* by the old `enable=prerelease == false` spelling. The distinction only bites once patch releases exist: publishing v0.9.1 **after** v0.10.0 is already out is an ordinary backport, and the old test would have moved `:latest` **backwards** onto the older image — silently downgrading every self-hoster on the one-command `docker-compose.yml` path at their next pull. The step writes its decision (and the reason) to the run summary; on a backport, `:latest` staying put is the correct outcome, not a failure to chase.
- **A release fans out to the CLI e2e (#448).** `release.yml`'s second job `dispatch-cli-e2e` (`needs: release`, so only once the image is actually in GHCR) cross-repo dispatches `vibexp/cli`'s `ci.yml` against the **latest CLI release tag** with `platform_image_tag=X.Y.Z`, and links the resulting run in its job summary — the same VibeXP Bot app mechanism as `publish-api-client.yml` (so the app needs **Actions: read & write** on `vibexp/cli`). It is **dispatch-and-link only**: the CLI verdict is never awaited, and because the job runs after the push it can never fail or roll back a release. A manual `workflow_dispatch` of `release.yml` deliberately does *not* dispatch downstream.
- **Patch releases come off a `release/X.Y.x` line branch, and fixes go to `main` FIRST (#747).** Minors are cut from `main` as always. A patch (v0.9.0 → v0.9.1) is cut from a line branch created **lazily** from the `v0.9.0` tag the first time that line needs a patch, then reused for 0.9.2+ — the tag already preserves the point, so there is nothing to gain from creating it at every minor. **Direction is the whole ballgame:** the fix merges to `main` through a normal PR, *then* `git cherry-pick -x` onto the release line. The git-flow direction (fix on the branch, merge back) is the one that regresses — a forgotten or conflict-mangled merge-back means the next minor silently reintroduces the bug you just shipped a hotfix for. `git cherry main release/0.9.x` must print no `+` lines; a `+` is a fix that exists only on the line. And when something genuinely must move back, **cherry-pick it — never merge the release branch into `main`**, which drags the line's history and can revert main-side state. Support window is the **latest minor only** (no 0.8.x once 0.9.0 ships); the docs site can only represent one "latest published release" anyway. **Contributors always PR to `main`** — backporting is a maintainer action, so never point an outside contributor at a release branch. Driven by the `release` skill's hotfix mode (`.claude/skills/release/SKILL.md`), which gates on all of the above.
- **A patch release must touch neither `openapi.yaml` nor `backend/migrations/` (#747).** Both constraints are structural, not stylistic. A spec change auto-publishes both API clients off **`main` merges only** (`publish-api-client.yml`), so a spec change on a release line produces a client corresponding to no released image — or worse, none at all. A migration is worse still: a self-hoster going 0.9.0 → 0.9.1 → 0.10.0 must land in the *same* schema state as one going 0.9.0 → 0.10.0, and since golang-migrate keys on the numeric prefix alone, a separately-numbered migration on the line forks that lineage permanently. If a fix needs either, **it is a minor** — ship 0.10.0 early instead of bending the patch. The release skill's Phase 0 refuses the release if the diff touches either path.
- **Release branches get their own CI, and the migration gate is base-aware (#747).** `ci.yml`'s push trigger is `[ main, 'release/**' ]` — PRs *into* a release branch already ran (the `pull_request` trigger is unfiltered), but without this the post-merge tip gets no run and we would tag a commit that never had its own CI. Cache **saving** stays pinned to `refs/heads/main` (a cache saved on another branch is visible only to that branch, so it would cost a full write for nothing), and `Sonar Scan` is **skipped on `release/**` pushes** — main is the coverage baseline and a line branch is main-as-of-the-last-tag plus cherry-picks, so scanning it would publish a second, permanently-lagging baseline. Correspondingly `check-duplicate-migrations.sh` takes an optional **third argument, the base branch** (default `main`), and the `migrations` job passes `github.base_ref`: comparing a backport's migrations against `main` is meaningless, and because `main` renumbers on every post-release consolidation (`002_`/`006_`/`011_consolidated`) it would fail *every* backport PR — training everyone to reach for the `migration-renumbering` label and stop reading the gate.

## Repository automations

Three `.github/workflows/*` keep the tracker and the VibeXP board (`vibexp/#3`) truthful with zero manual triage (issue #416). They are repo/board hygiene, not build/test:

- **`stale.yml`** (daily) — **issues only** (`days-before-pr-stale: -1`). No activity for **7 days** → `Stale` label + a warning comment; **14 days** → one reminder comment (deduped by a `<!-- stale-14d-reminder -->` marker); **21 days** → close with a final comment. Any genuine (non-bot) activity removes `Stale` and resets the clock. Issues labeled `pinned`, `epic`, or `security` are exempt. `actions/stale` owns only the 7-day marking; the later stages run in a `github-script` step keyed off the **`Stale`-label event** (not `updated_at`, which the reminder comment itself would bump — corrupting both the close window and un-staling).
- **`pr-linked-issue.yml`** (on `pull_request`) — **every PR must link an open issue.** Fails unless the PR has ≥1 linked **open** issue via `closingIssuesReferences` — add `Fixes #N` / `Closes #N` to the PR body or link it from the **Development** sidebar. A failing PR carries one explanatory bot comment. The `no-issue-needed` label is the escape hatch for trivial PRs. (It reports a status only; making it a *required* check needs a branch ruleset — a separate admin decision.)
- **`project-board.yml`** (on `issues: opened` + daily) — auto-adds issues to `vibexp/#3` and sets **Status=Backlog only when Status is empty** (never overwrites); a daily sweep also moves any **open** issue sitting in a **past iteration** into the current one (current/future iterations and Done/closed items untouched; iteration ids are resolved live — never hardcoded). Projects V2 writes use a **VibeXP Bot app** installation token (the default `GITHUB_TOKEN` can't write org Projects), so the app needs **Organization → Projects: Read & write** granted by an org admin; until then the workflow fails fast with a remediation message.

Third-party actions are SHA-pinned (matching `publish-api-client.yml`). Labels `Stale`, `no-issue-needed`, and `pinned` back these automations.

## Working agreement

- Branch off `main`, match existing style, run the relevant `make ...-lint` / `...-test` / build targets before committing, open a PR, let CI pass.
- **Branch naming:** `feature|patch|minor/{GITHUB_ISSUE}-{slug}` — prefix is one of `feature` (new functionality), `minor` (small improvements), `patch` (fixes/docs/chores); `{GITHUB_ISSUE}` is the number of the open issue the PR is linked to (every PR must link one); `{slug}` is a short kebab-case description. Example: `feature/416-stale-issue-automation`. **`release/X.Y.x` is reserved** for maintenance line branches (#747) — never name a working branch that way; the pattern drives `ci.yml`'s push trigger and the Sonar skip.
- **Backport PRs** keep the same naming (`patch/{issue}-{slug}`) and only change base: open them against `release/X.Y.x`, one `git cherry-pick -x <sha-from-main>` per PR, after the fix is merged to `main`. `-x` records the source SHA, which is what makes the two lines auditable.
- Pre-commit hooks are mandatory (see above); never use `--no-verify`.
- Don't commit secrets or gitignored generated artifacts.
